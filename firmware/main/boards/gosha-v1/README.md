# gosha-v1

Профиль `gosha-v1` — первая собственная точка прошивки `Гоша`, созданная как безопасная копия профиля `otto-robot`.

## Назначение

- сохранить исходный `otto-robot` как эталон сравнения;
- вынести собственные аппаратные и продуктовые правки в отдельный профиль;
- подготовить первую самостоятельную сборку `Гоша` без вмешательства в исходный профиль.

## Текущее состояние

- Профиль уже содержит собственные продуктовые параметры `Гоша`, экранный профиль, локальный управляющий контур и подтверждённый объединённый образ.
- На новом устройстве `2026-08-23` подтверждены `ESP32-S3` ревизии `v0.2`, вариант `non-camera`, `16 MB` flash-памяти и `8 MB PSRAM`.
- Полная установка потребовалась из-за несовместимой заводской таблицы разделов и выполнена только после полного резервного копирования flash-памяти.
- Программный канал левой руки на `GPIO8` подтверждён перекрёстным тестом.
  Неисправный физический сервопривод левой руки отключён от платы и должен
  оставаться отключённым. Прошивка, перезагрузка и неподвижные аппаратные
  проверки разрешены по `docs/HARDWARE_DEVELOPMENT_POLICY_RU.md`; движение
  требует отдельной команды.
- Полная аппаратная проверка опирается на документы верхнего уровня:
  - `../../../../docs/HARDWARE_MANIFEST_RU.md`
  - `../../../../docs/PIN_MAP_RU.md`
- Текущий безопасный release-кандидат включает
  `CONFIG_GOSHA_NO_MOTION_SAFE_PROFILE=y`. В этом режиме профиль поднимает
  голос, `Wi-Fi`, OTA/config, runtime events и локальный `WebSocket`, но не
  подключает сервоприводы, не выполняет boot `Home` и не регистрирует
  MCP-инструменты движения, servo sequence, `set_trim` и ручной
  `self.upgrade_firmware`. Замена прошивки во время работы также отклоняется в
  `Application::UpgradeFirmware()` до закрытия `protocol`, остановки `audio`,
  загрузки образа, записи flash-памяти или reboot. Удалённое MCP-действие
  `self.reboot` в этом профиле не регистрируется, а прямые MCP-вызовы
  `self.upgrade_firmware`, `self.reboot` и `self.assets.set_download_url`
  отклоняются до побочных эффектов. `CheckAssetsVersion()` в этом профиле не
  открывает `assets/download_url` на запись и не запускает живую замену
  ресурсов; `Assets::Download()` возвращает отказ до HTTP и записи
  flash-памяти. Уже установленный локальный assets-раздел применяется.
  Серверная команда `system.command == "reboot"` тоже отклоняется до
  `Application::Reboot()`. Возврат движения, удалённого reboot или удалённой
  замены assets допускается только отдельным аппаратным решением и отдельной
  сменой сборочного параметра.

## Ближайшие шаги

- сохранить Draft/Open состояние PR `#24`, а новые устанавливаемые кандидаты
  готовить в отдельной ветке с rollback и hardware evidence;
- подобрать совместимую замену левой сервы, сначала проверить её без качалки и нагрузки, выполнить `Home` и только затем установить механику;
- после замены провести малый тест руки штатным управляющим путём;
- продолжить подтверждение остальных строк аппаратного манифеста и карты выводов;
- для последующих выпусков использовать каноническую сборку `GOSHA_OTA_URL='<owner-only endpoint>' python3 scripts/release.py gosha-v1 --name gosha-v1`; скрипт не печатает значение endpoint и не хранит его в Git.

## Временная сборка безопасной нейтрали

Вариант `gosha-v1-safe-neutral-boot` предназначен только для отдельно
разрешённого владельцем возврата корпуса в нейтральную стойку. Он одновременно
оставляет включённым `CONFIG_GOSHA_NO_MOTION_SAFE_PROFILE` и добавляет
`CONFIG_GOSHA_SAFE_NEUTRAL_BOOT_PROFILE`.

- оба канала рук перед инициализацией контроллера заменяются на
  `GPIO_NUM_NC`, поэтому PWM на руки не подаётся;
- на варианте `non-camera` подключаются только четыре привода ног и ступней;
- при каждом запуске образ один раз подаёт на них нейтральное удержание
  `90` градусов и затем сохраняет PWM для удержания стойки;
- если обнаружен вариант с камерой либо неполная карта четырёх нижних
  приводов, все servo PWM остаются отключёнными;
- внешние инструменты движения, `Home`, `set_trim`, servo sequence, удалённые
  reboot/OTA и живая замена assets остаются закрыты no-motion профилем.

У сервоприводов нет обратной связи. Прошивка не знает фактический угол
свободного сустава и не может достоверно выполнить плавный переход из
произвольной сложенной позы. До запуска оператор обязан при снятом питании
поставить стопы плоско, приблизить ноги к нейтрали без усилия, удерживать
корпус и иметь немедленный доступ к отключению питания. При рывке, гуле,
нагреве, повторном reset или brownout питание отключается сразу.

Каноническая локальная сборка временного варианта:

```bash
GOSHA_OTA_URL='https://maintenance.invalid/firmware/' \
  python3 scripts/release.py gosha-v1 --name gosha-v1-safe-neutral-boot
```

Адрес `.invalid` служит только безопасной заглушкой для локальной сборки;
полученный образ не предназначен для удалённого обновления.

## Commissioning Live

`mode=commissioning` предназначен для первого live-шага одного привода, когда
у владельца ещё нет verified механической привязки и диапазонов. Такой профиль
не открывает полноценную анимацию: capabilities возвращают
`commissioning=true`, `calibrated=false`, limits каждого lower-body joint
строго `[-1,+1]`, `max_speed_dps <= 1`, measured pose и tilt остаются `null`.
Отдельный `mode=commissioning_right_arm` добавляет только правую руку
`arm_positive_x -> right_hand`, slot 5, GPIO12, `neutral_degrees=135`,
`direction=+1`. Правая рука в этом режиме принимает ровно symmetric ±5°
(`servo 130..140`) или явно заданный symmetric ±15° (`servo 120..150`);
default/sample остаются ±5°. Offline candidate под запрос «70° вверх» добавляет
только явный asymmetric range `[-70,+15]` (`servo 65..150`); он остаётся
commissioning-кандидатом, а не verified/calibrated диапазоном. Ноги/ступни
остаются strict ±1°, левая рука остаётся NC, скорость для commissioning —
1°/с.

Внутри одной сессии фиксируется начальная applied-поза и первый физический
канал, который отличается от неё. До STOP или watchdog другой физический канал
двигать нельзя даже после возврата первого в baseline; переход дальше чем на
фактический extent профиля от baseline также отклоняется: для lower-body это
1°, для старого right-arm ±5° это 5°, для явного right-arm ±15° это 15°,
для candidate `[-70,+15]` это 70°. Поэтому candidate может идти из нейтрали
к −70° или +15°, но не может пройти −70°→+15° как один 85° sweep внутри той же
сессии.
Профиль всё равно требует локальный access key, generated header вне Git,
совпадение pin/trim/neutral с runtime и те же no-motion/safe-neutral guards.

## Motion editor Live

`mode=motion_editor` — source-only режим для обычного редактора движений. Он
остаётся owner-defined и не считается verified calibration:
`commissioning=false`, `calibrated=false`. В одной authenticated session можно
вести все доступные суставы без one-joint lock. Текущий active set — 5 joints:
ноги `[-35,+35]`, стопы `[-30,+30]`, правая рука
`arm_positive_x -> right_hand`; `arm_negative_x`/`left_hand` остаются NC. Editor
profile принимает speed `1..10°/с`; UI default `5°/с` совместим.

Полный 3D-запрос правой руки `[-70,+55]` нельзя использовать с текущей
production нейтралью: `neutral=135`, `direction=+1` даёт servo `65..190`, а
серво-контракт остаётся `0..180`. Firmware не clamp'ит, не меняет нейтраль и не
подменяет углы. Full range проходит только при явно заданной достижимой
нейтрали, например synthetic `neutral=125` даёт servo `55..180`. Более узкий
правый range внутри `[-70,+55]` допустим только как явный owner/mechanical
profile; фактический диапазон виден клиенту через `joint_limits`.

В `motion_editor` `keepalive` и timer `Tick` не двигают суставы и не вызывают
`StepTowardTarget`; они только обновляют motion clock, чтобы idle не копил
delta для следующего POSE. Движение идёт только через POSE stream.
`initialize_right_arm`, auth/session/watchdog 300 мс, STOP без Home/detach и
no-motion/safe-neutral guards сохраняются.

## Live-настройка в редакторе движений

Ветка `codex/motion-live-20260906` содержит обработчик `gosha.motion.live.v1`
на локальном WebSocket `/ws`, порт 8080. Его клиент находится в
GOSHA_PLATFORM, `platform/motion_studio/`. На физическом роботе обработчик
пока не установлен. Точная установленная база — безопасная нейтраль
`baf0323d17db9f0635cf9ae64d79eb6f3c19af2c`.

Live-сообщения обрабатываются перед старым MCP-маршрутом и не вызывают
старые инструменты движения. Обычные сборки отвечают
`capabilities.motion_allowed=false`. Для разрешения сессии одновременно нужны:

- `CONFIG_GOSHA_MOTION_LIVE_LOCAL_OPT_IN=y`;
- сохранённые `CONFIG_GOSHA_NO_MOTION_SAFE_PROFILE=y` и
  `CONFIG_GOSHA_SAFE_NEUTRAL_BOOT_PROFILE=y`;
- локальный заголовок профиля, переданный через
  `-DGOSHA_MOTION_LIVE_PROFILE_HEADER=<абсолютный-локальный-путь>`;
- совпадение профиля с выводами, подстройками, подключёнными каналами и
  выполненным начальным удержанием нейтрали; в lower-body commissioning обе
  руки должны оставаться NC, в `commissioning_right_arm` и `motion_editor` левая
  рука остаётся NC, а правая доступна только после отдельного
  `initialize_right_arm`;
- работающий контроль потери связи и правильный ключ доступа.

Профиль готовится скриптом `firmware/scripts/prepare_live_profile.py` из
локального JSON. В нём обязательны `profile_id`, `access_key`, `max_rate_hz`
и четыре либо пять записей `joints`: `id`, `servo_key`, `pin`, `trim`,
`neutral_degrees`, `direction`, `min`, `max`, `servo_min_degrees`,
`servo_max_degrees`, `max_speed_dps`. Нейтраль lower-body текущего контроллера
— 90°, знак — 1 или -1.
Параметры берутся из проверенной механической калибровки; направления и
границы из 3D-предпросмотра её не заменяют. Привязка стороны модели к
`left_leg/right_leg/left_foot/right_foot` указывается явно. Для
`commissioning_right_arm` правый канал указывается явно как `right_hand`;
`arm_negative_x`/`left_hand` не входят.

Генератор вычисляет `calibration_id` как SHA-256 канонических проверенных
параметров. Изменение привязки, пределов или подстройки меняет этот идентификатор.
Необязательное одноимённое входное поле может только проверить ожидаемый SHA.
В заголовок попадает хеш ключа, сам ключ — только в локальный входной JSON.
Все эти файлы должны храниться вне Git. Пример команды из папки `firmware/`:

```bash
python3 scripts/prepare_live_profile.py local_only/verified-profile.json \
  --output local_only/gosha_motion_live_profile.h
```

Одна сессия принадлежит одному соединению. Номера команд возрастают строго;
чужие, старые и запоздалые пакеты не продлевают управление. Хранится только
последняя цель, без очереди макродвижений. Скорость изменения уставок ограничена
проверенным профилем и максимумом 30°/с, с дискретностью PWM в 1°. Через 300 мс
без допустимых команд изменение уставок прекращается. STOP завершает сессию
и сохраняет последнюю команду: без Home, новой позы или отключения опоры.
Открытие следующей сессии само по себе не двигает робота.

ACK и `stopped` возвращают все шесть полей `commanded_pose`, рассчитанные по
применённым программным углам. Дробный накопитель скорости не выдаётся за
реальный угол. `measured_pose` и `tilt` равны `null`: измерители положения и
наклона для нынешнего Гоши не подтверждены. Равновесие нужно будет оценивать
наблюдением после аппаратного допуска; автоматической стабилизации здесь нет.
Существующие ограничения OTA, reboot, assets и старых команд движения сохранены.

Проверки без робота:

```bash
python3 scripts/prepare_live_profile.py --self-test
python3 scripts/check_gosha_v1_motion_live_profile.py --self-test
g++ -std=c++17 -Wall -Wextra -Werror main/boards/gosha-v1/motion_live_core.cc \
  scripts/motion_live_core_host_test.cc -o /tmp/gosha-motion-live-tests
/tmp/gosha-motion-live-tests
```

Синтетический профиль из тестов и сборки с адресом `.invalid` не предназначены
для установки. Перед реальным запуском нужны наблюдения владельца за текущей
позой/гулом/нагревом, проверенная привязка приводов и отдельный аппаратный допуск.
